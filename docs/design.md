## 1. 誰が使い、何をしないで済むのか

**使う人**：リフォームの元請（現場に行く人。スマホ、手が汚れている、50代想定）。

**この製品の主張**：現場での入力を、数量だけにする。

現場でしか決まらないのは「どこを直すか」「現況」「寸法」の3つだけ
（→ 4章の業務フロー調査）。このうち **写真が「どこを直すか」と「現況」を記録する**。
残る「寸法」だけが入力欄として要る。

工事項目・単価・掛率の入力欄は**作らない**。
**単価を知っているのは下請であって元請ではない**（→ 4章）。埋めるべき人が違うものを、
埋めなくていい人に見せない。

### 経緯（2026-08-05）

初期の実装は「元請が金額を知っている」前提で、工事項目・数量・単位・単価・税区分・掛率の
入力欄を現場作業者に打たせる作りだった。これは前提から誤りで、作り直しが決まった。
詳細は `docs/failures.md` 2026-08-05「業務ドメインの設計を、実物を見ずに思い込みで決め、
確認するたびに全部外れていた」。

## 2. 差別化点（2026-08-05 確定）

**「図面の無い現場で、撮った写真がそのまま複数社への見積依頼になる」**

競合調査の結果、次の3つの接続が空いている。ここだけを看板にする。

**比較の範囲**：元請が下請・協力業者に見積を依頼する場面（＝書類①）に限る。
施主が複数のリフォーム会社に一括見積を依頼するマッチングサイト（リショップナビ等）は
**別の層**なので比較対象にしない。

1. **図面ではなく現場写真から始まる。** リフォームは元の設計図書が手元にないことが
   多い（→ 4章）。既存の写真→積算サービスが読むのは**間取り図**であり
   （公式ページに「積算したい間取り図をスマートフォンで撮影」と明記）、
   図面が無い現場が対象から漏れている。
2. **撮影が、そのまま下請への見積依頼になる。** ANDPADでは写真は施工管理、見積は
   受発注で別作業になっており、撮った写真がそのまま依頼になる導線が無い。
   写真de AI積算は撮影から送信までアプリ内で完結するが、**返ってくるのは自動積算の
   結果であって、下請に投げる見積依頼ではない**（公式ページに記載があるのは
   撮影→トリミング→寸法設定→フロア選択→物件名・メール入力の5ステップと、
   約5分での見積メール受信まで）。
3. **複数社への同時依頼が主眼。** 既存の受発注システムは「発注」の効率化であり、
   相見積を取って比べる設計ではない。

### 看板にしないもの

**建設業法対応を売り文句にしない。** 満たしていて当たり前の前提として静かに実装する。

理由：[ANDPAD受発注](https://andpad.jp/products/edi) が2021年4月に
[グレーゾーン解消制度](https://andpad.co.jp/news/427/)を用いて経済産業省・国土交通省に
建設業法施行規則13条の4第2項の技術的基準への適合を確認済みで、電子署名・タイムスタンプ・
電子帳簿保存法対応まで揃えている。流通総額は2年で614%成長。後発が同じ看板で正面から
戦う場所ではない。

（この判断に至る前、競合を調べずに「建設業法対応が売り文句になる」と提案していた。
→ `docs/failures.md` 2026-08-05「競合調査をせずに『これが差別化点になる』と断定し…」）

## 3. 書類は2種類ある

①と②は別書類。**②の使い回しではない。**

|  | ① 見積依頼書（元請 → 下請） | ② 御見積書（元請 → 施主） |
|---|---|---|
| 敬称 | **御中**（会社宛） | **様**（個人・施主宛） |
| 単価・金額欄 | **空欄**（相手が埋めて返す） | 埋まっている |
| 金額の大見出し | 無い（まだ決まっていない） | ある（御見積金額） |
| 本文 | 「下記の条件でお見積りをお願いいたします」 | 依頼文なし |
| 条件欄 | 依頼する側が提示（法定事項） | 提示する側が記載（工事条件・除外項目） |
| 法的な縛り | **建設業法の明示義務あり** | 特段の明示義務なし |

実物：[見積依頼書のテンプレート（アイピア）](https://aippearnet.com/column/wp-content/uploads/2025/10/%E8%A6%8B%E7%A9%8D%E4%BE%9D%E9%A0%BC%E6%9B%B8%E3%82%A8%E3%82%AF%E3%82%BB%E3%83%AB%E3%83%86%E3%83%B3%E3%83%97%E3%83%AC%E3%83%BC%E3%83%88_001.jpg)

設計案（実物6件・法令要件と照合済み）：
https://claude.ai/code/artifact/889f3363-0e45-4bc9-b0f0-5543394c6980

### ①の法的要件（建設業法）

**一次情報**：国土交通省「建設業法令遵守ガイドライン（第12版）— 元請負人と下請負人の
関係に係る留意点 —」（不動産・建設経済局建設業課、令和8年1月改訂、令和8年2月2日訂正版）
https://www.mlit.go.jp/totikensangyo/const/content/001979917.pdf
（掲載元一覧：https://www.mlit.go.jp/totikensangyo/const/sosei_const_tk1_000002.html ／
本文をPDFから直接確認した日：2026-08-05）

**書名が似た別のガイドラインと取り違えないこと。**「発注者・受注者間における建設業法令
遵守ガイドライン」（第8版）は発注者と受注者の関係を扱う別文書で、元請→下請の見積依頼を
定めているのは上記の第12版のほうである。

建設業法第20条第3項により、元請負人が下請負人に提示しなければならないのは、
同法第19条で請負契約書への記載が義務付けられている事項のうち**「請負代金の額」を除く
すべての事項**。うち「工事内容」について、元請負人が最低限明示すべき事項として
ガイドラインが挙げているのが次の**8項目**（原文の番号・表記に沿う）。

1. 工事名称
2. 施工場所
3. **設計図書（数量等を含む）**
4. 下請工事の責任施工範囲
5. 下請工事の工程及び下請工事を含む工事の全体工程
6. 見積条件及び他工種との関係部位、特殊部分に関する事項
7. 施工環境、施工制約に関する事項
8. 材料費、労働災害防止対策、建設副産物（建設発生土等の再生資源及び産業廃棄物）の
   運搬及び処理に係る元請下請間の費用負担区分に関する事項

具体的内容が確定していない事項については、**その旨を明確に示す**ことが求められる
（空欄で出すのではなく「未定」と書く）。

**見積期間**（建設業法施行令第6条。契約内容の提示から契約締結までに設ける期間）：

| 工事1件の予定価格 | 最低日数 |
|---|---|
| 500万円未満 | 1日以上 |
| 500万円以上 5,000万円未満 | 10日以上 |
| 5,000万円以上 | 15日以上 |

やむを得ない事情があるときに限り、下2つは**5日以内に限り短縮できる**。
下請が期間満了を待たずに見積書を交付した場合はこの限りでない。

**製品仮説（法的な断定ではない）**：リフォームは元の設計図書が手元にないことが多いのに、
法は「設計図書（数量等を含む）」の明示を求める。**現場写真＋数量が、その明示の実務上の
手段になりうる**のではないか、というのがこの製品の仮説である。
**現場写真＋数量が「設計図書」に該当するとは言えない**し、写真を送れば要件を満たす、
とも言えない。実際に送る書類2種が各要件にどう対応するかは、8章の実務者レビューで
確かめるまで確定しない。いずれにせよ2章のとおり、ここを看板にはしない。

## 4. 業務フロー（初回訪問 → 最終見積）

「毎回決めること」と「基本的に決まっていること」で分ける。決まっていることを毎回
打たせない、が設計の基準になる。

| 工程 | 毎回決める | 基本的に決まっている |
|---|---|---|
| 現地調査（1〜2時間） | 直す範囲／現況の劣化／寸法・施工面積／制約（搬入経路・管理規約・給排水や電気の位置） | 見るべきチェック項目／撮る写真の種類／記録の形式 |
| 拾い出し（数量拾い） | **数量だけ** | 工事項目の名前と単位（クロス張替え＝㎡、解体＝式 等） |
| **単価の決定** | 相手に聞かないと決まらない分 | 労務単価（国土交通省の歩掛りデータ・公共建築工事標準単価積算基準）／資材単価（建設物価調査会・経済調査会の刊行データ）／自社の実績単価表 |
| 諸経費 | ほぼ無し（率を掛けるだけ） | 率そのもの（会社ごとに固定） |
| 見積書の作成 | 宛名・工事場所・金額・工期 | 様式・列構成・支払条件・有効期限の日数・自社情報 |
| 提出→修正→再提出（3〜5日） | 修正内容 | プロセス |

**元請が下請に見積を依頼する業務は、法が前提にしている既存の業務である。**
建設業法第20条第3項は「元請負人が下請負人に見積りを依頼する」場面そのものを規律して
おり（→ 3章）、見積依頼書のテンプレートも業務ソフト各社が配布している。この製品は
その既存業務を自動化するものであって、新しい業務を持ち込むものではない。

**訂正（2026-08-05）**：ここには当初「単価の出所は3つあり、うち1つが協力業者への
問い合わせ。業界は既に『単価は下請に聞く』をやっている」と書いていたが、
根拠として挙げていた楽王のページが実際に書いているのは、労務単価＝国土交通省の歩掛り、
資材単価＝建設物価調査会・経済調査会のデータ、および**資材の取引業者**への定期的な
問い合わせであって、**協力業者（下請）への単価の問い合わせではなかった**。
出典が支持していない主張だったため、上のとおり書き換えた。

**リフォーム特有の難所**：元の設計図書が手元にないことが多く、既存撤去・廃材処分の
費用が読めない。図面だけで判断するのは危険とされ、現地を見ないと決まらない。

出典：
[リフォームにおける積算とは（楽王）](https://rakuoh.jp/contents/knowledge/home-renovation-cost-estimation.html/) ／
[リフォームの現地調査（リフォームガイド）](https://www.reform-guide.jp/topics/reform-genchichousa/) ／
[リフォームの流れ（リショップナビ）](https://rehome-navi.com/articles/51)

## 5. ②の様式（住宅リフォーム推進協議会 書式Ⅳ-1）

### 一次情報

**空欄の様式そのもの**：https://www.j-reform.com/publish/pdf_shosiki/mitumori.pdf
（1402版。`README.md` にも記載）

様式に**印字されている**もの：

- タイトル「住宅リフォーム工事／御見積書」、作成日欄
- 宛名（下線＋「様」）
- 注記「*設計料を必要とする場合は、工事項目に明記します」
- 請負者ボックス：請負者名／代表者／住所／印
- 表の4列：**工事項目｜摘要(仕様)｜（単価・数量・時間 等）｜金額**
- **最下行に「解体・廃棄物処理費」が固定行として印字されている**
- 集計3行：工事価格（税抜き）／取引に係る消費税等／合計（税込）
- 「■添付書類：見積内容を補足するため、打ち合わせシートは必ず添付します。」
- 「本見積書の有効期限は、　年　月　日までとさせていただきます。」
- 「※ この書類は大切に保管してください。」
- 担当者 印・サイン欄

**様式に無いもの（記入者の運用）**：大分類の見出し行（「1.床工事」「2.キッチン工事」等）は
様式には印字されていない。記入例や実際の見積書で広く使われている運用であって、
様式の定めではない。**この区別を混同しない。**

### 経路の異なる実物5件で確認した一致（2026-08-05）

1件では標準かどうか判定できないため、性質の違う5経路から集めて突き合わせた。

| 屋根・外装専門メディア | [MOTTOBE 表紙](https://drone-roofer.com/mottobe/wp-content//uploads/2021/10/07-1.jpg) |
| 会計・請求ソフト（工事専用でない） | [マネーフォワード 汎用見積書](https://biz.moneyforward.com/invoice/basic/wp-content/uploads/2021/11/%E8%A6%8B%E7%A9%8D%E6%9B%B8.png) |

**一致した（＝踏襲する）**：タイトル／宛名＋様（下線）／作成日（5件）、請負者情報＋社印
（5件）、見積金額を大きく単独で見せる欄（4件）、見積有効期限（4件）、
**項目／摘要／数量／単位／単価／金額の6列**（工事系4件すべて）、
大分類の見出し行でまとめる運用（内訳がある3件すべて）、諸経費を独立行（3件）、
小計→消費税→合計（3件）、備考列（3件中2件）、金額末尾の「-」＝改ざん防止（5件中3件）。

**ばらついた（＝標準ではない。こちらの裁量で決める）**：列数（4〜8列）、
表紙と内訳を1枚にするか鑑＋別紙に分けるか、**数量に実数を入れるか「1式」にして寸法を
摘要に書くか**（TOTOは工事を「1式」にして摘要に寸法。ホームプロは工事も実数）、
見積番号の有無、工事条件・除外項目の書き方。

**採用した判断**：共通の6列＋備考の7列。1枚にまとめる（デモで紙をめくらせない）。
数量は実数を入れる（数量欄を使わないと入力欄の意味が無くなるため）。

### 写真をどこに入れるか

**大分類の見出し行の直下**（例：「1. キッチン工事」の下にキッチンの写真）。

**写真は実物5件すべてに存在しない。ここだけが業界様式から外れる箇所。**
ただし様式には「打ち合わせシートは必ず添付します」という注記があり、補足資料を
添付する慣行自体は元からある。

未決：書類の中に埋め込むか、別紙にするか。デモのインパクトは前者、業界慣行への
忠実さは後者。

## 6. デモ用データの扱い

このアプリは**営業デモに使う**（「こういうアプリ要りませんか？」と見せる用途）。
特定業者の実運用ではないため、**「いつも使っている書類の現物」は存在しない。**

- Webから集めたサンプルを**参照**して、書類は自前で作る。
- **他社のテンプレートファイルは取り込まない**（`AGENTS.md` 公開前提5）。
  参照するのは構造だけ。参照した実物へのリンクはこの文書に残す。
- サンプルデータに実在の第三者を特定できる情報を使わない（`AGENTS.md` 公開前提2）。

## 7. 未決の設計判断

- **①の条件欄（法定7項目）をどこまで自動で埋めるか。**
  工事名称・施工場所は案件情報から自動。責任施工範囲・費用負担区分は定型文を事前設定。
  見積回答期限は金額から法定日数を自動計算できる。**全体工程と施工条件・制約が残る。**
  「写真を撮るだけ」を貫くなら定型文で埋めて後から直す形になる。
- 写真を書類に埋め込むか、別紙にするか（5章）。
- 現行の見積エディタ（手入力の明細）をどこまで残すか。
- 1明細＝1依頼＝1社 の現行設計を、複数社への同時依頼にどう作り直すか。
- 下請への送付手段はメール（LINE/Slack は売れるときに本番開発で調整する方針）。

## 8. 実運用の前に必ず通す工程

**実務者1人に、書類2種を現物レビューしてもらう。**

調査で取れるのは成文化された層（法令・公開書式・標準構造）だけ。実際にどの欄を空欄で
運用しているか、どういう依頼だと下請に無視されるか、といった習慣は文書化されていない。
デモまでは調査で足りるが、実運用の前にはこの工程を省かない。
