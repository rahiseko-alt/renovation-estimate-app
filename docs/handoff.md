# 引継ぎメモ（handoff）

セッションをまたぐ**揮発的な引継ぎメモ**。**このファイルは毎回上書き**（最新1件だけを保持する）。

- 製品の定義（誰が使うか・差別化点・書類の仕様・作り直しの設計）→ `docs/design.md`
- **実装の受け入れ条件・テスト方針・デバッグ方針・PRの区切り** → `docs/plan-rebuild.md`
- 過去の失敗の蓄積 → `docs/failures.md`（append-only・消さない）
- 開発の進め方・規約 → `AGENTS.md`

**恒久的な決定をこのファイルに書かない。** 上書きされて消えるうえ、`docs/design.md` /
`docs/plan-rebuild.md` と食い違ったときに、次のセッションが古い仕様を実装してしまう。

## ④まだ埋まっていない前提

- 依頼提示後に写真を追加したときの扱い（法的評価は未確認）

- 本番で実在の顧客情報を扱うときの社外ホスティング可否
- **法定③（設計図書＝写真＋数量）の充足判定条件**（未決）。
  **送信ゲートは③を検査していない**（`lib/db/submissionGate.ts` が見るのは
  法定④⑤⑥⑧の9スロットと⑦の12区分だけ）。写真が0枚・数量が全部0でも送信できる。
  実運用に出す前に、充足条件を一次情報から決めて判定とテストを足すこと。
  デモの範囲では、写真と数量を入れて見せるので露見しない。

## ⑤分かっているが直していないこと

- `pdf-actions.ts` が `getPricedEstimate` を通っていること自体は、自動検査で直接は
  捕まえられない。**PDFのバイト列から金額は読めない**（埋め込みフォントのグリフになる。
  今回実測して確認）。捕まえられるのは比較表の合計まで。Server Action を単体で叩く検査を
  作れば塞がる。
- `seedDemoData` は複数の insert を分けて投げるので、途中で失敗すると中途半端な行が残る
  （CodeRabbit の指摘）。1つのトランザクション（DB関数）に寄せると直る。
  デモは作り直しが効くので今回は範囲外にした。
- `docs/failures.md` の append-only を機械で止めていない（2回破りかけている）。
