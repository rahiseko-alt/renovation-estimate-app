# failures（失敗の蓄積ログ / append-only・消さない）

同じ失敗を繰り返さないための**蓄積型**ログ。handoff（`docs/handoff.md`・毎回上書き）とは
役割が違い、ここは**消さずに積む**。1件＝**日付＋事象＋根因＋教訓**。

---

## 2026-08-01 ルールファイルに「このリポジトリが何であるか」を書いて摩擦を生んだ

- **事象**：既存プロダクトを持ち込んだセッションで、AI が本題に入る前に「このリポジトリはテンプレ専用
  （ここで直接アプリは作らない）」と復唱し、作業を4択のメニューとしてユーザーに差し出した。さらに
  「デフォルト構成とぶつかる」「土台のブランチをどうするか」を都度ユーザーに判断させ、着手までに
  無駄な往復が発生した。
- **根因**：`AGENTS.md` を「書いている場所（テンプレ本体）」を基準に書き、コピー先で同じ文面が読まれる
  ことを勘定に入れていなかった。コピーは原本と同一ファイルなので、製品を作る場所で「ここで作るな」と
  読まれる。加えて、①分岐の判定基準が書かれていない（＝判定できないので選択肢として差し出す）、
  ②pnpm 決め打ちのチェックと「スタックは決めない」が同一ファイル内で矛盾、③「書き換えてよい」という
  許可の語感が許可待ちを誘発、が重なった。
- **教訓**：エージェント向けルールには **「今このリポジトリで何をするか」だけを書く**。来歴・位置づけ・
  目的といったメタな説明は人間向け（README）に置く。分岐を書くときは、**エージェントが単独で実行できる
  具体的な判定条件**を必ず添える。許可（〜してよい）ではなく指示（〜する）で書く。

## 2026-08-01 「無確認で実行してよい」を、判定条件の精度より先に広げた

- **事象**：上記改定の初稿が、「コードがある／スタック欄が未記入」なら無確認で取り込みを実行し同梱
  サンプルを削除する、という内容だった。この条件は**このリポジトリ自身に完全一致**し（`apps/web` と
  `packages/ui` が実在し、欄は未記入）、適用すれば自分のサンプルを自動削除する状態だった。削除対象も
  「`pnpm-lock.yaml`・`tsconfig.base.json` **等**」と無限定で、プロダクト自身が pnpm/TS 構成の場合は
  プロダクトの資産を消しうる。敵対検証のサブエージェントが指摘して発覚。
- **根因**：自律性（聞き返しを減らす）を上げることに寄せて、**無確認で許す操作の範囲を、判定条件の
  精度より先に広げた**。破壊的操作の許可は、判定を1つ間違えるだけで実害になる。
- **教訓**：無確認実行を許すルールを書いたら、**まず「そのルールを今このリポジトリに適用したら何が
  起きるか」を実際に当てて確かめる**。破壊的操作は対象を列挙で限定し（「等」を使わない）、判断が付か
  ないものは残す、削除は独立コミット、を必ず添える。あわせて、CI を書き換えるルールには
  `ci.yml` の集約ゲート job 名 `ci-green` の維持を明記する（`scripts/setup.sh` の必須チェック名と
  結合しており、消すと全 PR が永久 pending でマージ不能になる）。

## 2026-08-02 「記入済み実例」の欄に、実在を確認せずにファイルパスを書いた

- **事象**：`AGENTS.md` に「共通の文言・値の置き場所」欄を新設し、記入済み実例である
  `apps/web/AGENTS.md` のその欄に `apps/web/lib/estimate.ts` と書いた。実際の `estimate.ts` は
  PERT 見積りの純粋な計算エンジンで、画面文言も共有定数も持っていない。つまり**その置き場所は
  リポジトリに存在しなかった**。文言は `page.tsx` / `layout.tsx` / `home.test.tsx` に重複したままで、
  新設した「結合を増やさない」1（同じ文言を2箇所以上に書かない）に**実例自身が違反していた**。
  コミット前に自分でファイルを開いて発覚し、`apps/web/lib/content.ts` を新設して解消した。
- **根因**：欄の**書式**（何を書く欄か）を決めた勢いで、**値**（実際に何が書いてあるべきか）を
  コードを開かずにファイル名の語感から推測した。「見積りのアプリだから estimate.ts に定数がある
  だろう」という推測で、`AGENTS.md`「完了の証明」が禁じている自己申告そのものだった。
- **教訓**：ルールに新しい欄を足したら、**その欄を実際に埋めてみるまでがルール改定**。埋めた値は
  必ず対象ファイルを開いて確かめる（パスが実在するか、そこに本当にその役割があるか）。埋めようとして
  埋まらない欄が出たら、それは記入漏れではなく**リポジトリ側がまだルールを満たしていない**証拠なので、
  実体を作ってから書く。「該当が無いので『なし』」と「確かめていないので分からない」を混同しない。

## 2026-08-02 既存の仕掛けを「既にあるから」で残し、ユーザーの方針と突き合わせなかった

- **事象**：ルール改定で `.claude/settings.json` を差し替える際、提示された内容に `hooks` が無かったため
  「貼り替えると既存の Stop フック（`check-uncommitted.sh`）が消える」と指摘し、統合して残した。
  だがそのフックは**ターン終了ごとに未コミット・未push を検出して exit 2 で止める**もので、直後に
  ユーザーから「最大限サクサクやりたい。変に安全装置を増やすな」と言われ、1ターンで削除に至った。
  `out` から PR・マージを外す方針とも真正面から衝突していた。
- **根因**：「既存の安全装置は残すのが安全」を**それ自体で正しい判断**として扱い、ユーザーが何を
  最適化したいのか（速さか、堅さか）と突き合わせなかった。差分を見て「消える」ことは検出できたが、
  「そもそも要るのか」を問わなかった。既存物の保存は、現状維持なので判断したように見えて実は
  判断を飛ばしている。
- **教訓**：既存の仕掛けを残す判断も、新しく足す判断と**同じ重さで理由を言えること**。特に
  「毎回走って人を止める」種類のものは、残す前に**発火頻度と、それが止める対象**を書き出して
  ユーザーの方針と照合する。摩擦を生む仕掛けは、指摘のついでに黙って温存しない。

## 2026-08-03 squashマージ後、同じ作業ブランチへの追加pushが毎回non-fast-forwardで拒否された

- **事象**：PR を squash マージすると `main` 側には新しいコミットハッシュが刻まれる。その後
  同じ作業ブランチ（`claude/in-3do8qg`）に新しい変更を積んで `git push` すると、ローカルの
  ブランチ履歴（squash前の個別コミット群）と `main` の内容が噛み合わず non-fast-forward で
  拒否される、という現象が同一セッション内で3回連続発生した。`git push --force-with-lease` は
  ツール権限で拒否される設定になっており使えない。毎回「`origin/main` からブランチを作り直す
  → `git merge origin/main` で一度取り込む（コンフリクトは ours/theirs で解決）→ 新規コミットを
  `cherry-pick`」という手順で復旧したが、手順を忘れて `git reset --hard` だけで作り直そうとして
  同じ non-fast-forward に再度ぶつかったこともあった。
- **根因**：squash マージは意図的に履歴を1つのコミットに畳むため、作業ブランチ側の個別コミットとは
  祖先関係が無くなる。「同じブランチ名を使い続ける」という `in-out` skill の運用（作業中のブランチが
  あればそのまま使う）と、「PRごとにsquashで畳む」という運用が組み合わさると、この不整合が
  マージのたびに必ず起きる構造になっている。force push 不可という安全側の設定が、この構造的な
  不整合を「毎回人力で解きほぐす」形でしか回避できなくしている。
- **教訓**：squash マージを使うリポジトリでは、**マージ後に同じブランチへ追加コミットを積む前に
  必ず `origin/main` を fetch し、ブランチを作り直してから作業を始める**（`git checkout -B
  <branch> origin/main`）。既に作業ブランチに変更を作ってしまった後で気づいた場合は、
  「`origin/main` から新ブランチを作る → `git merge origin/main`（元のブランチ）→ 差分ファイルの
  conflict は ours/theirs で解決 → 新規コミットを cherry-pick」の順で復旧する。`git reset --hard`
  や生の `git push` を先に試して都度失敗してから対処するのではなく、squash マージ完了の通知を
  受けた時点で先回りしてブランチを作り直す。

## 2026-08-04 セキュリティ用の依存 override が、破壊的メジャーまで巻き上げて lint を壊した

- **事象**：`package.json` の `pnpm.overrides` にあった `"brace-expansion@<5.0.9": ">=5.0.9"` により、
  `minimatch@3` が要求する `brace-expansion@^1.1.7` まで v5 に置き換えられた。v5 は
  `module.exports = { expand }` の名前付きエクスポートに変わっており、`require("brace-expansion")` を
  関数として呼ぶ v1 系の使い方が壊れる。結果 `eslint .` が
  `TypeError: expand is not a function` で異常終了し、lint が実行そのものをできなくなった。
  override を外したところ `brace-expansion@1.1.18`（脆弱性修正済みの版）に自然解決し、
  `pnpm audit --audit-level moderate` も «No known vulnerabilities found» になった。
- **根因**：脆弱性の修正版が複数のメジャー系列に分かれて出ている（1.1.12 / 2.0.2 / 3.0.1 / 4.0.1）のに、
  override を「最新のひとつ」に一本化した。脆弱性を塞ぐことだけを見て、
  **その版が呼び出し側と同じ API を保っているか**を見ていない。
  さらに、テンプレート作成時点では lint 経路がこの依存を踏まなかったため、
  壊れていることに気付かないまま残った。
- **教訓**：依存の override は**呼び出し側のメジャーを跨がせない**。塞ぎたい脆弱性に対して、
  各メジャー系列の修正版を個別に指定するか、そもそも自然解決で足りていないかを先に確かめる。
  override を足したら `pnpm audit` だけでなく **lint・test・build まで通して**から入れる。
  「監査が緑」は「動く」ではない。

## 2026-08-04 起動スモークが、前回の残骸サーバを検査して結果を偽った

- **事象**：`scripts/smoke.sh` の原型で、`pnpm --filter web start &` の PID に `kill` を送って
  後始末したつもりだったが、実際に停止したのは pnpm のラッパーだけで、子の `next-server` が
  ポートを掴んだまま生き残っていた。次に検査を回すと、起動待ちのポーリングが**残骸サーバの 200**を
  掴んで「起動した」と判定し、そのまま古いビルドを検査した。CSP を実装した直後に
  「CSP ヘッダが無い」と 4 件落ちたが、実際にはコードは正しく、落ちていたのは検査の方だった。
  逆に、新しい秘密鍵で署名したセッションが古いサーバでは通らず、1 件だけ落ちるという
  紛らわしい出方もした。
- **根因**：検査対象を「ポート番号」でしか特定しておらず、**そこに居るのが自分が起動した
  プロセスか**を確かめていなかった。加えて、プロセスグループを作らずに親だけ kill したため、
  後始末が成立していなかった。「落ちた原因はコード側にある」と決めつけて、
  検査基盤そのものを疑うのが遅れた。
- **教訓**：外部プロセスを起動して検査するスクリプトは、**開始前にポートが空いていることを確かめて、
  埋まっていたら検査せずに落とす**。後始末は `setsid` でプロセスグループを作り、
  グループごと止める。実装を直す前に「検査が本当に対象を見ているか」を先に確かめる。
  なお、この種のデバッグで `pkill -f <文字列>` を使うと、**その文字列を含む自分の実行シェルまで
  巻き添えで殺す**（コマンドライン全体が照合対象のため）。`pkill -f "next[-]server"` のように
  自分自身に一致しない書き方にする。

## 2026-08-04 proxy が付けるヘッダを HEAD リクエストで検査して、無いと誤判定した

- **事象**：CSP の検査を `curl -sI`（HEAD）で行ったため、`next.config.ts` が静的に付ける
  HSTS 等は見えるのに、`proxy.ts` が付ける `Content-Security-Policy` だけが返らず、
  「CSP が無い」と判定した。GET で取り直したら正しく付いていた。
- **根因**：ヘッダを見るだけなら HEAD で十分だろうという思い込み。実際にはヘッダを**誰が**
  付けるかで挙動が変わる。ブラウザが実際に行う操作（GET）と違う方法で検査していた。
- **教訓**：受け入れ条件は**利用者と同じ操作**で確かめる。ヘッダの検査は
  `curl -s -D - -o /dev/null`（GET してヘッダを出す）を使う。

## 2026-08-04 完了報告した直後に、外部レビューと独立検証で実害のある欠陥3件が見つかった

- **事象**：フェーズ0を「受け入れ条件オールクリア」として報告した commit `78ebf0e` に対し、
  CodeRabbit の自動レビューと `independent-verifier` サブエージェントを並行してかけたところ、
  自分のローカル検証・CIともに緑だったにもかかわらず、以下が実際に壊れていた。
  1. **`/projects` が静的プリレンダされ、CSP の nonce を受け取れず自分のスクリプトを
     自分でブロックしていた**（script 15本中0本にnonce、うち6本はインラインscript）。
     nonce はリクエストごとに `proxy.ts` が生成するが、Next.js は動的レンダリングされた
     ページにしか nonce を届けない。`/projects` は動的APIを使っていなかったため
     ビルド時に静的化され、原理的に nonce が届かない状態だった。
  2. **`lineAmount` が特定の小数の組み合わせで1円少なく計算されていた**
     （例: 1.4×1400円 → 電卓では1,960円、実装では1,959円）。既存テストは
     「浮動小数点誤差で1円ずれない」を1方向（真値より大きく出るケース）でしか
     検証しておらず、逆方向（真値より小さく出るケース）を1件もカバーしていなかった。
  3. `readSessionValue` が、署名は正しいが中身が `null`/配列のペイロードで
     `TypeError` を投げて 500 になっていた（署名検証が先なので認証バイパスではないが、
     「形が違えば null を返す」という関数自身の契約に反していた）。
  smoke.sh の nonce 検査もトップページしか見ておらず、上記1を検出できない作りだった。
- **根因**：
  - (1) は、CSP nonce と Next.js の静的/動的レンダリングの相互作用という**フレームワーク側の
    暗黙の前提**を検証せずに実装した。ローカル・CIのスモークが `/` だけを見ていたため、
    2つ目以降の保護ページで初めて起きる欠陥を機械検査が最初から検出できない構造だった。
  - (2) は、既存テスト「浮動小数点の誤差で1円ずれない」が**片方向の実例だけで
    「直した」と判断した**。実装が特定の入力でしか検証されていないのに、
    テスト名は一般化された主張（「ずれない」）をしていた。
  - (3) は、`JSON.parse` が `"null"` や配列も例外を投げずに通すことを見落とし、
    `typeof payload.sub` の前に `payload` 自体の形を確かめていなかった。
- **教訓**：
  - **CSP nonce のような「ページ間で挙動が変わりうる」仕組みは、代表1ページだけでなく
    保護対象の全種類（動的/静的になりうる全ルート）を検査に含める。** 1ページ緑でも
    他ページが壊れている前提で検査を作る。
  - 「◯◯で1円ずれない」のような性質を主張するテストは、**その性質が壊れる具体的な
    反例を先に列挙してから**書く。片方向の実例1つで「直った」と判断しない。
  - `JSON.parse` の戻り値は `null`・配列・プリミティブも通る。プロパティに触る前に
    必ず `typeof value === "object" && value !== null && !Array.isArray(value)` を確かめる。
  - **自分の完了報告を鵜呑みにせず、フェーズごとに自動レビューツールと、実装者とは
    独立に受入条件を再実行する検証エージェントの両方を通す**運用は、今回3件とも
    実害のある欠陥を拾えたので継続する。特に独立検証は BigInt 総当たりでの
    検算という、通常のテストでは書かない検証方法で (2) を見つけた。

## 2026-08-04 浮動小数点の誤差を「許容幅」で吸収する方式は、閾値をどう調整しても反例が作れた

- **事象**：`lib/calc.ts` の金額計算（数量×単価などの掛け算）で、浮動小数点の丸め誤差を
  「真値に近い整数へ寄せる」方式で塞ごうとし、CodeRabbit のレビューのたびに新しい反例で
  破られる、という段階を5回繰り返した。
  1. 固定の許容幅（`FLOAT_ERROR_MARGIN = 1_000_000` 分の1円）で近い整数に丸める → 
     `quantity: 1.9999996` のような**本物の細かい端数**まで誤って丸め上げてしまう反例が出た。
  2. 固定幅をやめ、`Number.EPSILON` に比例した相対許容幅（ULP相対）に変更 → 
     値が大きいと許容幅自体も大きくなり、`quantity: 999999999999.999` のような大きい値で
     **本物の端数（約0.000977円）より許容幅（約0.00177円）の方が大きくなり**、
     結局また誤って丸め上げる反例が出た。
  3. ここで「閾値をどれだけ調整しても、必ず別の入力で破られる」と判断し、閾値調整をやめて
     `BigInt` による整数の正確な演算（`exactMultiplyTrunc`/`exactPercentTrunc`）に構造ごと
     置き換えた。数量は1/1000単位の整数にスケールしてから BigInt 乗算・除算する。
  4. BigInt化した後も、`unitPrice: Number.MAX_SAFE_INTEGER` のような極端な入力では、
     BigInt演算自体は正確でも**最後に `Number()` へ戻す時点で** `Number.MAX_SAFE_INTEGER`
     を超え、別の整数に化ける反例が出た（`Number(27021597764222973n)` → 
     `27021597764222972`、1ずれる）。単価に現実的な上限（10億円）を設け、
     `assertSafeAmount` で変換後に安全整数かを毎回確かめるようにした。
  5. 単価の上限を設けた後も、`calcEstimate` 内の集計ループ（`directCostSubtotal += amount` 等）
     が**素の `number` の `+=`** だったため、11行加算・10行減算のように**期中の部分和が
     `Number.MAX_SAFE_INTEGER` を一時的に超えてから範囲内に戻る**入力で、最終値が
     `Number.isSafeInteger` を通過するにもかかわらず真値と1〜2円ずれる反例が出た
     （`node -e` で自作検証：1個あたりの真値 `900719925474099` を11回加算すると
     `9907919180215088`、そこから同じ値を10回減算すると `900719925474098` になり、
     残るべき真値 `900719925474099` と1円ずれる）。集計自体も BigInt のまま積み上げ、`number` へは
     範囲確認後に一度だけ変換する（`bigIntToSafeAmount`）構造に直した。
- **根因**：どの段階でも「今回報告された具体的な反例1つ」だけを直し、**「閾値やヒューリス
  ティックで浮動小数点誤差を吸収する」という方式そのものが原理的に反例を許す**ことに
  途中まで気付かなかった。浮動小数点の誤差と、桁数の決まった「本物の端数」は、
  どちらも「整数からわずかにずれた値」であり、値の見た目だけでは区別できない。
  区別できないものを閾値で選り分けようとすれば、閾値をどう動かしても
  「本物の端数を誤検出する」か「誤差を見逃す」かのどちらかの反例が必ず作れる。
- **教訓**：**金額のような整数計算に浮動小数点の許容幅・閾値調整で対処するのは
  構造的に直らない**。反例が2回出た時点で「次の反例を潰す」のをやめ、
  入力を固定精度の整数にスケールしてから BigInt 等の任意精度整数演算に
  置き換える方向へ設計ごと変える。BigInt化した後も、**BigInt→number の変換点**

  見える」ことは「計算の途中で精度が失われていない」ことの証明にならない。

## 2026-08-05 squash マージ後の未マージ判定に `git log origin/main..<旧ブランチ>` を使う手順を書いた

- **事象**：PR #14 で、squash マージ後の復旧手順として
  「`git log origin/main..<旧ブランチ>` で未マージのコミットを確認して cherry-pick する」
  と書いた。**これは誤り。** squash マージは元のコミット群を1つの新しいコミットに
  畳むため、元のコミットは `origin/main` の祖先にならない。したがってこの範囲指定は、
  **既に squash 済みで main に取り込まれているコミットまで「未マージ」として列挙する**。
  この手順に従うと、PR 全体の変更をもう一度 cherry-pick して重複させる可能性がある。
  CodeRabbit の指摘で発覚。上の 2026-08-05 の項目と同じコミットで手順を訂正した。
- **根因**：`A..B` が「B にあって A に無いコミット」を意味することは知っていたが、
  **squash によって「内容は取り込まれているが、コミットとしては祖先でない」状態が
  生まれる**ことを、手順を書く時点で結び付けなかった。squash マージの性質は
  2026-08-03 の項目で自分が書いていたにもかかわらず、それを復旧手順の側に
  適用していない。
- **教訓**：squash を使うリポジトリでは、**取り込み済みかの判定にコミットの
  祖先関係（`git log A..B`）を使わない。内容の差分（`git diff A B`）で見る。**
  復旧の判断手順は以下にする。
  1. `git fetch origin main <旧ブランチ>`
  2. **その PR を畳んだ squash コミットの SHA を特定して控える**（マージ通知や
     `git log origin/main --oneline` の該当行）。以降の比較はこの SHA に対して行い、
     `origin/main` を基準にしない。**`origin/main` はその後のマージで先へ進むため、
     基準に使うと「main 側で後から入った無関係な変更」まで差分に現れ、
     旧ブランチ由来の作業と区別が付かなくなる。**
  3. `git diff <squash の SHA> <旧ブランチ>` を**全文で**見る（`--stat` の行数だけ
     では、その差分が運ぶべき作業なのか判断できない）。差分が無ければ運ぶものは無い。
     squash 済みの内容はここに現れない。
  4. 差分がある場合、それが squash 後に足した作業。対応するコミットを
     `cherry-pick` するか、差分を手で作り直す。**squash 済みのコミットは
     `git log` の範囲指定では除外できない**（2で書いた祖先関係の話）ので、
     どのコミットを運ぶかは 3 の差分の中身を見て決める。
  5. リモートブランチを削除する前に、ローカル・リモート双方に固有のコミットが
     無いことを両方向で確認する（`git log <旧ブランチ>..origin/<旧ブランチ>` と
     `git log origin/<旧ブランチ>..<旧ブランチ>`）。確認せずに削除すると、
     リモートにしかない作業を失う。

## 2026-08-05 検査が到達していない層について「正常」と結論づけ、誤って報告した

- **事象**：上記の本番障害を調査する過程で、エージェント（Claude）が
  `GET /q/aaaaaaaa-...`（UUID形式でない文字列）を叩いて 200 が返ったことを根拠に、
  「DBへの問い合わせが成功しているのでDBは正常」と報告した。**これは誤り。**
  `getQuoteRequestByToken` は先頭で `if (!isUuid(token)) return null;` と早期returnするため、
  UUID形式でない文字列では Supabase クライアントを一度も呼ばない。つまりこの検査は
  DBに到達しておらず、テーブルが1つも無い状態でも同じ 200 を返す。実際にはDBは
  壊れたままで、UUID形式のトークンで叩き直したところ 500 が返って発覚した。
- **根因**：「/q はDBに到達する経路だ」というルート単位の理解で止まり、
  **その関数が入力によってDBに到達しないことがある**（ガード節・早期return）を
  見ていなかった。呼び出し先のコードを読まずに、経路の名前と HTTP ステータスだけで
  「どの層まで検証できたか」を判断した。200 が返ったことは「その経路が例外を出さずに
  応答した」ことしか意味しないのに、「その経路が通る全ての層が正常」と読み替えている。
- **教訓**：**検査が「通った」ことを根拠にする前に、その検査が本当に検証したい層まで
  到達しているかを、コードを読んで確かめる。** 早期returnやガード節（形式チェック・
  キャッシュ・機能フラグ等）がある関数は、入力を選ばないと何も検証できない。
  「この入力でこの経路を通ると、どの関数のどの行まで実行されるか」を辿ってから
  入力を決める。今回なら、`isUuid` を通過する UUID形式の文字列でなければ
  DB層の検証にはならない（実在しない UUID でよい）。同じ理由で、この経路を
  監視に組み込むときも入力がUUID形式であることが検査の前提条件になる。
