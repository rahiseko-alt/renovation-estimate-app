# flows（全工程のフロー図）

**この文書は、実装（`apps/web/`）から起こした工程図である。** 製品として何を決めたかは
`docs/design.md` が正で、ここには**決定を書かない**（同じ決定を2箇所に書くと、片方だけ
古くなったときにどちらが正か分からなくなる。`AGENTS.md`「結合を増やさない」1）。

ここが持つのは「**いま実装が、どの順で何を通るか**」だけである。値・文言・判定条件の
実体は各図の下に置き場所を書いた。**経路を変えたらこの文書も同時に直す。**

対象範囲：**デモ経路と通常経路の両方**。両者は別のアプリではなく、
**同じ工程を、入力を飛ばして通るか、人が埋めながら通るかの違い**でしかない。

---

## 0. まず言語化する（図の前に、言葉で全工程）

### 登場するのは3者

| 誰 | ログイン | 触る画面 | 何をする |
|---|---|---|---|
| **元請** | **要る**（`/q` 以外の保護対象） | 案件・写真・法定項目・依頼・比較表・見積書 | 現場を撮り、数量を入れ、下請に依頼し、返ってきた単価を採用し、施主向けの見積書を出す |
| **下請** | **要らない**（token だけが資格情報） | `/q/<token>` のみ | 依頼された明細に数量・単価を入れ、必要経費の内訳を添えて返す |
| **施主** | — | 無し（アプリに入らない） | 出来上がった御見積書PDFを受け取る |

保護範囲は `apps/web/proxy.ts` の `PROTECTED_PREFIXES`（`/projects` `/estimates`
`/masters` `/settings` `/subcontractors`）1箇所が正。

### 工程は7フェーズある

**フェーズ0：準備（事業者ごとに1回だけ）**
ログインし、会社設定（請負者名・代表者名・住所と、法定④⑥⑧の定型文7スロット）を入れ、
下請台帳（社名・メール）に依頼先を登録する。**この2つが空だと、後段が成立しない**
——請負者情報は書類の印字欄そのものであり、下請台帳が空だと依頼の宛先が選べない。

**フェーズ1：案件を作る**
施主名と現場住所を入れる。作成と同時に、会社設定の定型文がその案件の法定項目スロットへ
**複製される**（参照ではない。参照だと、会社設定を直した瞬間に既に送った案件の内容まで
遡って変わる）。空の定型文は書き写さない（空で書くと「未入力」ではなく「記入済みで中身が空」に
なり、送信ゲートの意味が変わる）。複製に失敗したら案件ごと消して巻き戻す。

**フェーズ2：現場（写真と数量）**
箇所を選んで写真を撮る。ブラウザ側で圧縮してから送り、サーバは
**認証 → 所有者確認 → 箇所の検証 → 形式の検証 → 大きさの検証**を通してから
Storage に置き、`photos` に行を入れる。行の作成に失敗したらオブジェクトを消す
（逆順にすると、参照されない実体が残る）。表示は300秒の署名付きURL。
数量は見積エディタで明細に入れる。

**フェーズ3：法定項目**
法定項目9スロットに **3状態**（記入する／未定を明示／未入力）を、施工条件・範囲リスト
12区分に **○／×**を付ける。「未定」は利用者が明示的に選んだときだけ入る値で、
入力し忘れの穴埋めには使わない。

**フェーズ4：依頼を出す**
送り先（複数社）と予定価格帯を選んで送る。サーバは
**送信ゲート**——9スロットが全部「記入済み」か「未定を明示」で、12区分が全部
「未検討」でないこと——を**画面とは別にもう一度**判定する（Server Action は直接叩ける）。
通れば依頼グループを作り、社ごとに **token・予定価格帯・回答期限・対象明細の範囲**を
持つ依頼を作る。回答期限は「提示日時＋帯ごとの法定日数」。
**アプリが出すのはリンクまで。** 送付そのものは手持ちの手段で行う。

**フェーズ5：下請が答える（ログイン不要）**
`/q/<token>` を開く。見えるのは**工事名称・施工場所・回答期限・依頼された明細**だけで、
施主名・売価・掛率・原価・他社の単価は**そもそも戻り値の型に入っていない**。
明細ごとに数量・単価を入れ、必要経費の内訳（材料費・労務費・法定福利費・安全衛生経費・
建退共・作業日数・元請支給材料の付記）を添えて返す。依頼の状態が `responded` になり、
2回目以降は「回答済み」の表示になる。

**フェーズ6：比較して採用する**
明細を縦、社を横に並べた表になる。最安に印が付く。**1明細につき採用は1社まで**で、
明細ごとに違う社を採れる。選び直しも取り消しもできる。採用ぶんの合計がその場に出る。

**フェーズ7：見積書を出す**
保存されている明細に、**採用した社の原価単価を読むたびに重ねて**金額を出す
（`estimates` に書き戻さない。書き戻すと、採り直し・回答の訂正のたびに整合を自前で持つことになる）。
会社設定の請負者情報を載せてPDFを生成し、ブラウザが受け取る。

### デモは、この7フェーズを「作った状態」で始める

トップの「デモを触ってみる」は **Server Action ではなく素のフォームPOST**である
（Server Action の呼び出し先IDはビルドごとに変わり、古いページを開いたままの
ブラウザから押すと無反応になる。実際に起きた）。POST を受けたサーバは、
同一オリジンを確かめ、使い捨ての `demo:<uuid>` でセッションを発行し、
**フェーズ0〜6の結果を6波の書き込みで一気に作る**——会社設定・案件・下請3社・
明細・法定9スロット・施工条件12区分・依頼グループ・3社の依頼（回答済み）・
3社の回答・明細ごとの採用まで。だから利用者が着地した時点で、比較表には既に
3社の単価が並び、採用も済んでいる。

**飛ばしているのは入力であって、工程ではない。** 3タップ目の見積書は、
通常経路とまったく同じ `generateEstimatePdfAction` を通る。

## 2. デモ経路の処理フロー（同じ工程を、作った状態で始める）

上の図の**フェーズ0〜6を6波の書き込みで作る**のがこれ。**別の工程ではない。**

```mermaid
flowchart TD
  A(["トップの「デモを触ってみる」<br/>= 素のフォームPOST（Server Action にしない）"])
  A --> B{"Origin と x-forwarded-host が一致するか"}
  B -->|"いいえ"| BX["403"]
  B -->|"はい"| C{"既にデモ中<br/>かつ デモの中身の版が一致するか"}
  C -->|"はい"| C1["作り直さず、自分の案件へ戻す"]
  C -->|"いいえ"| D["demo:&lt;uuid&gt; を発行<br/>（版が古いだけなら同じ識別子のまま作り直す）"]
  D --> E["セッションCookie（6時間）<br/><b>署名の中にも失効時刻を入れる</b>"]
  E --> F["seedDemoData"]

  subgraph SEED["seedDemoData（直列に待つのは6回。増やすと1タップ目が伸びる）"]
    direction TB
    W1["波1：後始末<br/>（新しい識別子なら消す対象が無いので飛ばす）"]
    W2["波2：会社設定 / 案件 / 下請3社 を同時に"]
    W3["波3：見積明細 / 法定9スロット / 施工条件12区分 / 依頼グループ を同時に"]
    W4["波4：3社ぶんの依頼を1回で（状態は responded）"]
    W5["波5：3社の回答 と 明細ごとの採用 を同時に"]
    W6["波6：回答明細（3社 × 明細数）を1回で"]
    W1 --> W2 --> W3 --> W4 --> W5 --> W6
  end

  F --> SEED
  SEED --> G["303 で /demo/&lt;projectId&gt;/photo へ"]
  C1 --> G
  G --> H["応答を返した<b>後</b>に、期限切れのデモを掃除<br/>（失敗してもデモは止めない）"]

  G --> I(["写真を撮る / 写真なしで進む"])
  I --> J["/projects/&lt;id&gt;/comparison<br/>3社の単価が既に並び、採用も済んでいる"]
  J --> K(["見積書PDFを出力 = 通常経路と<b>同じ</b> generateEstimatePdfAction"])
```

**採用まで作っておく理由**：3タップの経路に「採用」のタップが無いので、
採用が無いと見積書が全行0円になる（実際にそうなっていた）。

**掃除が届かない場合がある**（掃除そのものが失敗したとき／以後もう誰もデモを
始めないとき／写真の実体を消せずその案件を次回に回すとき）。「溜まらない」とは言えない。
線引きの理由は `docs/design.md` 6-1。

## 3. ユーザー操作フロー（人が何をするか）

レーンを3者に分ける。**アプリの外で起きること**（リンクを渡す・PDFを渡す）も
点線で書く。ここを図から落とすと、アプリが送信までやっているように見える。

```mermaid

  subgraph MOTO["元請（現場に行く人・スマホ）"]
    direction LR

    M2["会社設定と下請台帳を<br/>入れる（1回だけ）"]
    M3["案件を作る<br/>施主名・現場住所"]
    M4["箇所を選んで<br/><b>写真を撮る</b>"]
    M5["<b>数量</b>を入れる"]
```

## 5. この図が意図的に書いていないこと

事実として、いま実装に**無い**もの。図に描くと「あるように見える」ので、ここに文字で置く。

- **送付そのもの**。アプリが出すのはリンクまでで、メール送信もSMSも実装していない。
- **法定③（設計図書＝写真＋数量）の充足判定**。送信ゲートが見るのは④⑤⑥⑧の9スロットと
  ⑦の12区分だけで、**写真が0枚・数量が全部0でも送信できる**。充足条件が未決のため
  （`docs/design.md` 7章）。
- **期限を過ぎた回答の扱い**。回答期限は書類に印字するが、期限後の回答を止める判定は無い。
- **写真のスナップショット**。依頼後に元請が写真を足し引きしたときの扱いが未決。
- **一覧の件数上限**。`lib/db/` の一覧系は1000件を超えた分を黙って落とす。
- **社印**。様式には印欄があるが、画像を預かる仕組みがまだ無い。
