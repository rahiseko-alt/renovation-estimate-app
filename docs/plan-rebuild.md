# 作り直しフェーズの実装計画（受け入れ条件・テスト・デバッグ）

## Context

この計画は**実装をSonnetに渡す前提**で書く。判断の根拠は `docs/design.md`（commit `68357bd` 時点）に全て入っている。**実装者は着手前に design.md を通しで読むこと。この計画は design.md を要約しない。**

なぜ作り直しになったか：初期実装は「元請が金額を知っている」前提で、工事項目・単価・掛率の入力欄を現場作業者に打たせる作りだった。前提から誤りだった（`docs/failures.md` 2026-08-05）。正しい前提は「単価を埋めるのは下請」で、現場での入力は数量だけ。

規模：現行4,950行のうち文字通り触らないのは約800行（16%）、改修が約4,150行、**新規3,000〜4,500行**。現行とほぼ同量を新たに書く。

この計画が決めるのは **①フェーズの区切り ②各フェーズの受け入れ条件 ③テスト方針 ④デバッグ方針** の4つ。設計そのものは design.md が正。

## 実装者への3つの約束（これを破ると作り直しになる）

1. **design.md に根拠が無い事項は実装しない。手を止めて報告する。**
   「たぶんこうだろう」で業務ドメインを決めた結果、確認するたび全部外れた履歴がある（`docs/failures.md` 2026-08-05）。暫定実装＋TODOコメントも不可（暫定値が既成事実になる）。
2. **緑にするためにテスト・lintを削除・無効化・緩和しない**（`AGENTS.md`「完了の証明」）。落ちたら実装側を直す。
3. **証拠は外部事実のみ。** CIのrun URL / commit SHA / 公開URL。自己申告は証拠にしない。

## PR-A：スキーマ ＋ DB層

### 作るもの

`supabase/migrations/` に新規マイグレーション。**テーブルごとに `enable row level security` と `service_role` への明示 `grant` の2行を必ず書く**（`supabase/migrations/20260805022403_init.sql:9-13,25-31` に「新しいテーブルは service_role であっても自動では権限を持たない」と明記。忘れると黙って全機能が壊れる）。

1. **明細行の安定ID** — `estimates.lines` は jsonb 配列。**本番に既存行があるので backfill マイグレーションが要る**。
2. **法定項目スロット** — design.md 3章の13〜14スロット。**1スロット3状態**（値あり／未定を明示／未入力）。**状態列と本文列を分ける**（`text NULL` 1本でも文字列 `"未定"` でも表現できない）。
3. **会社設定** — 請負者名・代表者・住所・印、法定④⑥⑧の定型文の初期値。
4. **下請台帳** — 社名・メール。
5. **依頼グループ** — グループ（提示日時を持つ）と、社ごとの依頼（宛先・トークン・予定価格帯・回答期限・対象明細の範囲）。

`apps/web/lib/db/` に対応モジュール。既存の作法を踏襲する：
- 公開する型は `lib/db/types.ts`。画面は `lib/db/` の公開関数だけを通す（直接クエリを書かない）
- `COLUMNS` 定数で列を明示列挙（`select *` を書かない）
- `toXxx(row)` で snake_case → camelCase に変換
- 所有者チェックは `ownerId` で行い、他人のIDを知っていても取れないこと

**下請向けの投影型を明示的に作る。** `getQuoteRequestByToken` は現在 `markup_rate` と `owner_id` を含む行全体を返している（`lib/db/quoteRequests.ts:14-15,122-134`）。テンプレート駆動で「持っている値を全部出す」方向に変わるとそのまま漏洩経路になる。**トークンから引ける戻り値の型に、他社の単価・掛率・売価・原価・施主名を含めない。**

## PR-B：書類UI（スパイク先行）

### B-1. スパイクを先に出す（**保存もDBも無い使い捨て**）

**目的は1つだけ：書類ビュー＋シートが実機のスマホで成立するかを外部事実にする。**

design.md 7章の計算値：A4縦（793.7 × 1122.5 CSS px）を幅375pxに収める倍率は0.47。本文16px → 実効7.6px、タップ対象48px → 実効22.7px（WCAG 2.2 の最小24pxを下回る）。`transform: scale()` は computed font-size を変えないので iOS Safari の自動ズームも効かない。

**スパイクの中身**：様式ベタ書き、1箇所だけ、保存なし、ルート1つ。

**確認は実機のスマホで行う。** Vercel のプレビューURLを実機で開く（エミュレータで済ませない。仮想キーボードのレイアウトはOS/ブラウザで違う）。

**スパイクの受け入れ条件**（人が触って判定する。ここだけは機械判定にしない）：

| # | 条件 |
|---|---|
| S1 | 書類が「書類の形」に見える（縮小しても様式と分かる） |
| S2 | 行ブロックを**親指で**押せる。押し間違えない |
| S3 | シートが出たら本文16px・タップ48pxで、拡大せずに数量を打てる |
| S4 | シートを閉じると書類の該当セルに値が入ったのが**見える** |
| S5 | 写真枠のカメラマークを直接押せる |
| S6 | 200%まで拡大しても情報・機能が失われない |

**S1〜S5 のどれかが崩れたら、本実装に進まず報告する。** 書類ビューを諦めるか、別の見せ方にするかは設計判断であり実装者が決めることではない。

### B-2. 印刷をスパイクに載せる

**①見積依頼書のPDFは作らない。** 画面＝HTML、印刷＝ブラウザ（`@media print` + `@page { size: A4 }` + `window.print()`）。描画器を1つにすることで「画面と印刷がずれる余地」を構造的に消す。理由は design.md 7章（文字幅の計測方法・禁則と折り返しの有無・改ページの主体・座標系がいずれも違う）。

**印刷用CSSはリポジトリに1行も無い**（`@media print` は0件）。新規に書く。

**実際に紙に出して確かめる。** ここまでで `AGENTS.md`「入口から出口までを1回通す」に相当する。

### B-3. テンプレートを抽出する

スパイクが通ってから、**現物から**テンプレート層を抽出する。先に作ると語彙を想像で決めることになる。

- **テンプレートに絶対座標を持たせない。**「上から順に並ぶブロックの列」＋「ブロックごとのパラメータ」
- **文言の住所を分ける**：紙に印字される文字はテンプレートだけが持つ。画面のUI文言は `apps/web/lib/content.ts` だけが持つ。`ESTIMATE_TOTALS_TEXT` / `ESTIMATE_COLUMNS` / `ESTIMATE_DOCUMENT_TEXT` / `DEFAULT_DISPOSAL_ITEM_NAME` は**テンプレート側へ移す**（複製ではなく移動）
- **依存の向きを固定**：テンプレートは content.ts を import しない。content.ts はテンプレートを import しない
- テンプレートは①と②の2つ作る
- 分割の目安（`max-lines: 300`、`eslint.config.mjs:16-19`）：`lib/doc/schema.ts`（型だけ）／`lib/doc/templates/quote-request.ts`／`lib/doc/templates/estimate.ts`／`lib/doc/render/html.tsx`

## テスト方針

### 既存の作法（そのまま踏襲する。逸脱しない）

- `apps/web/tests/` 配下。`environment: "node"`。**testing-library は使わない**
- `import { describe, expect, it } from "vitest";` を**毎ファイル**書く（`globals` 未設定）。フックはアルファベット順
- import の順序：Node組込み → 外部パッケージ → vitest →（空行）→ 相対パスの自前モジュール
- **テストデータはデフォルト値＋spread のファクトリ関数**：
  ```ts
  function line(partial: Partial<EstimateLine> = {}): EstimateLine {
    return { kind: "item", name: "クロス張替え", /* ... */, ...partial };
  }
  ```
- **コンポーネントは `renderToStaticMarkup` で HTML 文字列にして `toContain`**（`tests/home.test.tsx:11-13`）
- **文言はリテラルで書かず `lib/content.ts` から import して比較**（`tests/home.test.tsx:5,14`）。例外はエラーメッセージのみ（正規表現リテラル）
- `it` の名前は**日本語の平叙文で「何を守るか」**、理由を括弧で添える（例：「appendEstimateLineを並行で呼んでも両方の行が残る（後勝ちで消えない）」）
- **境界値は「上限ちょうどは通す／1つ超えたら投げる」をペアで書く**
- 検算の根拠は必ずコメントに残す
- スナップショットは使わない
- ファイル分割は行数ではなく**意味の塊**で（`max-lines: 300` が鳴っても行数で割らない）

### DB を使うテストの作法

- **接続コードをテストに書かない。** `lib/db/*` の公開関数を呼ぶだけ。接続は `getSupabaseClient()` が env から作る
- **`beforeEach`／`afterEach` による掃除を書かない**（既存3ファイルとも0件）。代わりに次で汚染に耐える：
  1. `const OWNER_A = "owner-a@example.com"; const OWNER_B = "owner-b@example.com";`
  2. 各 `it` が自分でデータを作る
  3. **一覧の検証は件数ではなく `some()` の包含／非包含**
- **モックにしない。** ローカル Supabase に実際にクエリを出す（`AGENTS.md`）

### 新しく書く必要がある型のテスト（前例が無い）

**「レスポンスに禁止キーが含まれない」検査はリポジトリに1件も無い。** A6 / C2 で新規に書く。`Object.keys()` を回して禁止キーの非存在を assert する形にし、**なぜその検査があるか**をコメントに残す（下請に売価が渡ると相見積の前提が崩れる）。

### 中身のないテストを置かない

`AGENTS.md`「完了の証明」。型が通るだけのテスト、常に真になる assert を書かない。

## デバッグ方針

1. **計算のズレは、まず単体テストで再現させてから直す。** 画面側で辻褄を合わせない
2. **落ちたら実装を疑う前に、検査が対象を見ているかを先に確かめる。** 前例：残骸サーバを検査して結果を偽った（`docs/failures.md` 2026-08-04）／`/q/<32文字>` が `isUuid` の早期returnでDBに触らず200を返し「DBは健全」と誤報告した
3. **ヘッダの検査は GET で行う**（`curl -s -D - -o /dev/null`）。HEAD では `proxy.ts` が付けるヘッダが返らない
4. **E2E が落ちたらトレースを見る。** `trace: "retain-on-failure"`（`playwright.config.ts:19`）。CIで回す前に**手元で再現させる**（1周2〜3分をCIで待たない）
5. **`pkill -f <文字列>` を使わない。** 自分の実行シェルまで巻き添えで殺す。`pkill -f "next[-]server"` のように自分に一致しない書き方にする
6. **PDF／印刷物は生成物を実際に開いて目視する。**「保存が成功した」は「正しく描画された」ではない（`docs/failures.md` 2026-08-04 のフォントサブセット化事故）
7. **情報漏れは DevTools の Network でレスポンスを直接見る。目視で済ませず自動テストに落とす**
8. **失敗したことは `docs/failures.md` に追記する。既存行を消さない。訂正も追記でやる**

## 検査ハーネスに条件を追加する手順

### HTTP で判定できる → `scripts/smoke.sh`

- 単純な一致：`check "ラベル" 期待値 "$(curl -s -o /dev/null -w '%{http_code}' "${BASE}/path")"`
- 本文照合：`curl -o "${WORK}/x.html"` してから `expect_contains "ラベル" "文字列" "${WORK}/x.html"`
- 複合条件は `case` で自前判定。**失敗枝で `echo "  FAIL ..."` と `FAILURES=$((FAILURES + 1))` を必ず両方書く**
- **空文字を `grep -qF` に渡すと何にでもマッチして誤OKになる。** 先に空チェックする（`scripts/smoke.sh:245-249` の教訓）
- ログイン済みが要るなら `-H "Cookie: rea_session=${VALID}"`（`VALID` は232行で生成済み）
- 複合検査を新設するなら `check_csp_and_nonce`（`scripts/smoke.sh:154-197`）を雛形にする

### 画面操作が要る → `apps/web/e2e/full-flow.spec.ts`

- 目的ごとの `async function` に切り出し、本体テストから順に呼ぶ
- ロケータは `getByRole` / `getByLabel` を第一選択。CSS に落とすときは理由をコメントに残す

- **「壊れたとき実際に赤くなる経路」を通すこと。** DBに触らない経路だけ増やしても意味が無い
- **現在のDB到達検査は `/q/<uuid>` の200に依存している。** 回答画面を作り直すとき、**DBに触る前に早期returnする実装にすると監視が何も検証しなくなる**（`docs/failures.md` 2026-08-05 の事故の再発）。新テーブル（会社設定・下請・グループ・法定項目）に到達する検査を足す
